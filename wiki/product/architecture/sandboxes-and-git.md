# Sandboxes and git policy

Each [instance](../models/instance.md) works in its **own git worktree** of each code repo of the project it opens, never in the CEO's checkout: a repo is checked out for an agent only once it needs it ([Opening a repo](#opening-a-repo)), and a worktree idles on no branch at all, so an agent owns a branch only once it works on something ([Branches](#branches)). Only a team lead's branches (`lead/<project>/<team>/*`) can be requested for merging into one of the CEO's branches, and only the CEO's action merges them. The [Git block](./building-blocks.md#8-git-git) creates the worktrees on the host; the [session runner](./session-runner.md) mounts them into the instance's container. **Git belongs to Foreman: agents only read it.** Every git write (a commit, a merge, a new branch) is a team tool that Foreman runs on the host ([below](#agents-and-git)). The project's knowledge base is different: one live checkout of the [project repo](../models/project-config.md), shared by every agent ([below](#project-knowledge-base)).

**Phasing:** worktrees and branches per agent arrive in [Terminal multiplexer](../../backlog/epics/terminal-multiplexer.md) (epic 1); the `switch`, `commit` and `merge` tools, and hand-offs that name a branch, in [Messaging and hand-offs](../../backlog/epics/messaging-handoffs.md) (they need the agent link). **Decided: in epic 1 agents can't commit**: the CEO drives each session by hand and looks at the uncommitted work in each worktree; integration detection, checks and pushes to the forge in the [Git epic](../../backlog/epics/git.md).

## Layout

- **Worktree:** `<workspace>/agents/<agent>/<repo>/` for each code repo of the [project](../models/project-config.md#the-project-record) the agent opened, created on the host with `git -C <repo path> worktree add` when it does ([Opening a repo](#opening-a-repo)); until then the folder doesn't exist (an empty one would read as an empty repo). The code repo itself is wherever the CEO keeps it; Foreman writes only in its `.git`. A worktree shares its repo's object store and refs: nothing is copied, and every branch any agent creates is at once visible to the others and to the CEO. One team works on a project at a time, so worktree paths never collide; a later team's agent of the same id takes over the earlier one's worktree ([Team definition](../models/team-definition.md#schema)).
- `<workspace>/agents/<agent>/` is the instance's **sandbox**: its working directory, holding its worktrees. The project repo is not in it: agents see it at its real path, `<workspace>/project/` (the CEO, 2026-11-02). It lives in the project's [workspace](../models/project-config.md#the-workspace), a folder of the CEO's, where the CEO can look at the agent's work and run it (the CEO, 2026-10-28). A workspace is never inside a code repo, so nothing has to be git-ignored. Running an agent's code on the host has two caveats, told to the CEO: dependencies the agent installed in its Linux container (native `node_modules`, wheels) don't run on macOS, and the CEO's own install would break the agent's; and editing there while the agent works turns into its uncommitted changes.
- The harness's own files (its config, conversations, the login's mount point) are not in the sandbox: they are in `~/.foreman/harness/<project>/<agent>/`, readable by the CEO only ([Harness adapters](./harness-adapters.md)).
- The project repo `<workspace>/project/` never gets agent worktrees: it is the live, shared knowledge base.
- **The project's files** `<workspace>/files/`, kept whatever team is deployed (the CEO, 2026-11-06): `files/inbox/`, the CEO's files for the agents, read-only for them; `files/shared/`, the agents' data that outlives a task and a team, read and written by every agent of the project. Both are made at each agent start (and when the CEO opens one), and the [session prompt](./session-prompt.md#template) names them. Not git: no history, no review. An agent's sandbox root (outside its worktrees) is its own folder that persists too; `files/shared/` is the one the whole team shares. A project made before workspaces has none.
- A project made before workspaces has its sandboxes at `~/.foreman/sandboxes/<project>/<agent>/`, each with its `.harness/` inside, and its project repo at `~/.foreman/projects/<name>/`, until it is moved (legacy, [Project config → The workspace](../models/project-config.md#the-workspace)).
- **A located repo:** when the CEO points a moved code repo at its new path (Locate, [Project config](../models/project-config.md#the-project-record)), each existing worktree follows it on its next start (`git worktree repair`). A repo missing or changed blocks starting the project's agents until then.
- **Two projects, one repo:** a code repo may be in several projects, and the same team may be deployed on any of them at once (the CEO, 2026-11-03): every agent branch carries its project (`wt/<project>/…`, `lead/<project>/…`), so nothing collides in that repo's `.git`. Branches named before then (`wt/<agent>/…`, `lead/<team>/…`) stay as they were, out of the review flow: an agent `switch`es to a topic of its own and `merge`s an old one in to carry its work over.

## Branches

- **Idle: no branch** (the CEO, 2026-11-12). A worktree is made **detached** at the head of its repo's **default branch**, and an agent between pieces of work sits there, owning no branch: branches exist only for work. Git lets a branch be checked out in only one worktree at a time, so no agent checks out the default branch, or any other of the [CEO's branches](../features/pipeline-and-merges.md#where-a-merge-goes), itself; a detached checkout has no such limit. Nothing is committed while detached: `commit`, `merge` and `set_submodule` ask for a `switch` to a topic first. Until 2026-11-12 every worktree was made on a **home branch** (`wt/<project>/<agent>/main`, the lead's `lead/<project>/<team>/integration`); those left are ordinary branches of their agent's now, cleaned up like any other.
- **Topic branch** `wt/<project>/<agent>/<topic>` (e.g. `wt/ledger/tove/LED-44`, the topic usually a card id): where a member does one piece of work. Agents can't create branches themselves: `switch(branch)` has Foreman switch the agent's worktrees to it, creating it from the default branch (or from `from`: any branch or commit) the first time ([Agents and git](#agents-and-git)).
- **Lead branches** `lead/<project>/<team>/<topic>` (e.g. `lead/ledger/atlas/settlement-v2`): where the lead integrates hand-offs, any number of them, each reached (and made the first time) with `switch(branch)`; the lead never has `wt/` branches. They are the only source of merge requests, each into one of the CEO's branches (the default branch unless the lead names another), one open merge request per lead branch at a time. The team is part of the name because teams follow one another on a project (one at a time), and their branches stay.
- **The CEO's branches** are every branch of a code repo but an agent's (`wt/*`, `lead/*`): each repo's default branch (`main` when it has one; chosen per repo, see [Repos](../features/repos.md)) and any other the CEO's git account makes (a release branch, say). They change **only by the CEO's decision**: Merge (Foreman merges on the CEO's click), a PR merged on the forge, or the CEO's own git; Foreman never merges on its own, and no agent makes or writes one.

At each agent start ([Agent runtime](./agent-runtime.md#instance-lifecycle)) its worktrees already opened are reused as they are (relinked when their repo moved, an idle one brought up to its default branch); none is made. Since every worktree shares the repo, a branch of the CEO's that moved is visible to all of them as soon as the repo has it.

### Opening a repo

An agent's worktree of a repo is made the first time the agent needs it (the CEO, 2026-11-12: a team on many repos made a branch, a worktree and every submodule's checkout per agent per repo at each start, most never touched). Until then the agent reads the repo through its `.git`, mounted read-only at its real path like every repo's (`git -C <repo path> log main`, `git -C <repo path> show main:src/x.go`, `git -C <repo path> grep -n foo main`): looking around needs no checkout. A repo is opened:

- **explicitly**, with **`open(repo)`**, for an agent that wants the files on disk (to run them, or read many);
- **implicitly**, by any git tool that needs the worktree: `switch` opens the repos that already have the branch it goes to, `merge` those that have the branch it merges, `set_submodule` its repo. `commit`, `discard` and `abort_merge` act only on repos already open (there is nothing to commit in one never opened); `handoff`, `request_merge` and `prune` read branches, not worktrees, and open nothing.

A repo opened joins the agent's others: on the branch they are on (made from the repo's default branch when it lacks it, as `switch` does), or detached at the default branch while they are idle (or when it is the first). Its submodules are then checked out ([Submodules](#submodules)). Opening an open repo changes nothing. A `switch` to a new branch with no repo open refuses (`open(repo)` first: Foreman can't guess which repos the work is in). A repo added to the project later is opened the same way; a worktree is never removed by the agent (the CEO's Clean up does that).

**A deployment resumes; new work starts from the default branch** (the CEO, 2026-10-22). Stop then Deploy brings the same team back to the same worktrees and branches; branch names are never salted per deployment, as topics already keep pieces of work apart, and `switch(<new topic>)` starts each new one from the default branch (or from the branch or commit named with `from`). So that leftovers never get in the way:

- **Idle desks follow the default branch.** A detached worktree with nothing uncommitted, whose commit is in the default branch's history, moves to the default branch's head (`Git.Freshen`): at each agent start (deploy, wake, restart) and after every merge into the default branch, not into another branch ([Pipeline and merges → Merge to a target](../features/pipeline-and-merges.md#merge-to-a-target)). A worktree on a topic stays as it is: the agent resumes it, or switches to its next topic, which starts from the default branch.
- **Work not wanted goes cleanly.** An agent drops what it didn't commit with `discard()`; the CEO drops a dismissed review's branches with Dismiss ([Pipeline and merges → Review and merge](../features/pipeline-and-merges.md#review-and-merge)). Either way a copy is kept ([Backups](#backups)).

Stopping a deployment keeps the worktrees on disk; they are removed (`git worktree remove`) only on an explicit CEO action: the Team section's **Clean up** ([Project deployment → Earlier teams](../features/project-team.md#earlier-teams)), which removes those holding nothing uncommitted, and the `wt/*` branches whose work is all merged ([Pipeline and merges → Merge to a target](../features/pipeline-and-merges.md#merge-to-a-target)), of agents running nowhere. A branch still checked out in a kept worktree can't be deleted, so it goes when that worktree is removed.

### Cleaning up branches

Branches pile up: every topic, every hand-off. Three ways delete them (the CEO, 2026-11-11), all under one rule:

- **The agents' `prune(branches?)`** ([Team tools](./team-tools.md)): in each code repo, the caller's merged and superseded branches go, and a branch of its own named in `branches` even unmerged. The lead's also deletes its teammates' merged ones, and those superseded by another branch of that **same** teammate (`-draft` inside `-final`). A teammate's work held only by someone else's branch, or by none, is never the lead's to delete: only its owner deletes it (the CEO, 2026-11-11: pruning must never break another agent's work).
- **The CEO's branch cleanup**, over all of a project's code repos at once ([Repos → Branch cleanup](../features/repos.md#branch-cleanup)): every agents' branch of the project, and every legacy one, whatever its state; and the CEO's own merged or superseded branches (never the default branch, its or that of another project with the same repo, nor one by a long-lived name, `main`, `master`, `trunk`, `develop`, `development`, `dev`, `staging`, `production` or `prod`, whatever the default is; never one unmerged: it may be work in progress Foreman can't see). Deleted locally only: a copy on a remote stays. And, ticked one by one, a branch checked out in a **stray worktree** (a folder in no project's agents' sandboxes, nor the CEO's checkout: an old workspace's, or one since deleted): that worktree is removed first (`git worktree remove`), unless it holds changes not committed or a merge under way; what git ignores in it goes with its folder. Agents never remove a worktree.
- **The Team section's Clean up** ([Project deployment → Earlier teams](../features/project-team.md#earlier-teams)): the merged `wt/*` branches of agents running nowhere, with their worktrees.

**Where a branch's work stands** (`standing`, the same everywhere; deleting a merged or superseded branch loses no commit):
- **Merged**: all of it is in the history of a branch of the CEO's, or **upstream**, in a remote's branch as last fetched (the CEO, 2026-11-11: work merged on the forge counts before the CEO pulls; a branch's own copy upstream, `origin/<the same name>`, doesn't count), or it is in a **merged review's kept head** (`refs/foreman/decided/<mr>`, the commit the CEO merged, kept forever, of any project with the repo; the CEO, 2026-11-11: a squash leaves the lead's integration commits out of main and moves the lead branch on, so a teammate's branch it carried is held by nothing else; a rejected or withdrawn review's doesn't count) **with every line it changed still there**: its own diff, from where it left the review's target, undoes cleanly on that head (`Git.Survives`; the CEO, 2026-11-11: resolving a conflict the lead may have dropped part of it, which the review never showed, so history alone would over-delete; one reworked since is not merged either), or merging it into the default branch of any project with the repo, or into a branch some merge request of theirs went into or landed on, would change nothing (squash-aware).
- **Superseded**: not merged, but all of it is in another agents' branch (the CEO, 2026-11-11). Of two branches at the same commit, each holds the other: standing is read as each is deleted, so the second is no longer superseded and stays.
- **Unmerged**: some of it is nowhere else.

**The rule:** a branch someone has checked out (in a worktree: an agent's WIP, or simply the branch it is on, any project's agent; or the CEO's checkout) never goes; one in a stray worktree only by the CEO's pick, as above, nor one whose review is open, nor one an open review merges into (any project with the repo). The check is made under the repo's lock as the branch is deleted (`Git.DeleteBranch`, `ErrCheckedOut`), so a `switch` to it meanwhile can't lose it; deleting never touches a worktree. Each head is kept under `refs/foreman/cleaned/<time>/<branch>` first ([Backups](#backups)): once a superseded branch's holder is deleted too, that copy is all that's left of it.

**Whose branch:** `wt/<project>/…` and `lead/<project>/…` are that project's. A **legacy** branch (`wt/<agent>/…`, `lead/<team>/…` from before branches carried their project, or one carrying a project Foreman no longer has) is any project's to clean; another existing project's is never listed.

Not built: deleting merged branches **automatically**, after a merge or when a deployment ends ([After a merge: clean up](../../backlog/after-merge-cleanup.md)).

## Backups

What Foreman throws away, it keeps first, as a ref under `refs/foreman/<kind>/<time>/…` (time as `2026-10-22T09-30-00Z`, UTC): out of the branch list, restorable by hand, and deleted **30 days** after it was made (at Foreman's start, then hourly, and whenever a new one is made in that repo). A ref under `refs/foreman/` whose name carries no time is left alone: `refs/foreman/decided/<merge request>`, the head a merge request had when it left open, kept for good so its review still shows its diff, and so a merged one still counts a branch it carried as merged after a squash ([Cleaning up branches](#cleaning-up-branches)) ([Reviews → Decided](../features/reviews.md#decided)).

| Kind | What | Made by |
|---|---|---|
| `dismissed/<time>/<review>/<branch>` | a dropped branch's head | Dismiss, dropping its branches (`closed/` before 2026-10-22, until pruned) |
| `dismissed/<time>/<review>/<branch>@uncommitted` | what the worktree holding it hadn't committed (a merge not finished included), as a commit on its head | the same |
| `discarded/<time>/<agent>/<repo>` | what the agent hadn't committed, as a commit on its branch's head | `discard()` |
| `cleaned/<time>/<branch>` | a deleted agents' branch's head | `prune()`, the branch cleanup, Clean up ([Cleaning up branches](#cleaning-up-branches)) |

A copy of what wasn't committed is made through an index of its own (`GIT_INDEX_FILE`), so it records every file as it was (conflict markers included) and leaves the worktree's own index alone; files ignored by `.gitignore` aren't in it. A copy is never written over another: two made in the same second fail instead. To restore one: `git restore --source=<ref> -- .` in the worktree, or `git branch <name> <ref>`.

## Mounts

Everything at the **same path as on the host** ([Session runner](./session-runner.md#podman-engine-production)), so a path an agent names is one the CEO can open, and the Direct engine (no mounts) sees the same files (the CEO, 2026-11-02; the project repo was at `<sandbox>/project` before):

| Host path | In the container | Mode |
|---|---|---|
| `<workspace>/agents/<agent>/` (the sandbox: its worktrees) | same path; the working directory | rw |
| `<repo path>/.git` (each code repo, at its real path) | same path | **ro** |
| `<workspace>/project/` (the live project repo) | same path | rw for the lead, ro for the others |
| `<workspace>/project/.git` | same path, over the mount above | **ro** for every agent |
| `<workspace>/files/inbox/` (the CEO's files for the agents) | same path | **ro** |
| `<workspace>/files/shared/` (the agents' shared data) | same path | rw |
| `~/.foreman/harness/<project>/<agent>/` (its harness folder, 0700) | same path | rw |

A worktree's `.git` is a file pointing at `<repo path>/.git/worktrees/<name>` by host path, so git works inside the container only because the repo's `.git` is mounted at that same path. A submodule's `.git` file points into that same mount (`.git/worktrees/<name>/modules/<path>`), so it resolves there too ([Submodules](#submodules)). The CEO's working files (the code repo outside `.git`) are never mounted, and no agent ever touches the CEO's checkout or checks out a branch there. Foreman's own merge runs in it only when it has the target checked out, so its files move with that branch ([Pipeline and merges → Merge to a target](../features/pipeline-and-merges.md#merge-to-a-target)).

**Writes outside the mounts are not blocked** (the CEO, 2026-10-23). The rest of the container's filesystem is its own writable layer: a write there succeeds, reaches nobody, and is gone when the container restarts. That includes the folders around each repo's `.git` mount, at the repo's real path. It's accepted rather than closed with a read-only root: what an agent writes there can't be committed (commits run in its worktrees), so work that matters ends up in the sandbox, and what doesn't matter is lost harmlessly. Caches and tool settings under `$HOME` live in the same layer and last until the container is removed.

## Agents and git

**Agents read git; Foreman writes it.** Every repo's `.git`, the project repo's included, is mounted read-only, so inside the container `git status`, `diff`, `log`, `blame` and `show` work, and every git write (`commit`, `checkout`, `branch`, `merge`, `rebase`, `push`) fails. Writes go through [team tools](./team-tools.md#tools), which Foreman runs on the host in the caller's own worktrees:

- **`open(repo)`**: makes the agent's worktree of a code repo, the first time it needs one ([Opening a repo](#opening-a-repo)).
- **`switch(branch)`**: switches the agent's open worktrees (and opens the repos that already have the branch) to one of its own branches (`wt/<project>/<agent>/<topic>`, or `lead/<project>/<team>/<topic>` for the lead), creating it, if it doesn't exist yet, from `from` (any branch, a remote's branch such as `origin/main` after `fetch()`, or a commit) in each repo that has it, and from the default branch elsewhere or without `from`: made at that commit, with no upstream; so an agent can also go back to earlier work. A lead can keep several lead branches, and so several merge requests, at once.
- **`commit(commits)`**: for each repo the agent names, with its own message, stages everything changed there and commits it on the branch checked out there, authored as the agent (`<Name> <agent.invalid>`, author and committer: the CEO's identity never signs an agent's work, and its commits carry `commit.gpgsign=false`: [Signing](#signing)). Repos not named keep their changes (the CEO, 2026-10-17). The lead may name `project`, the live project repo.
- **`merge(branch)`**: merges a named branch (the lead's, the CEO's, a teammate's: any branch) into the agent's worktrees. On a conflict the markers stay in the files; the agent resolves them and calls `commit`, which concludes the merge. Agents never rebase: branches are shared, and tracking follows commits.
- **`abort_merge()`**: backs out of an unfinished merge, branch and files as before it.
- **`discard(repos?)`**: throws away what the agent changed and didn't commit, in each repo it names (all when none): the files go back to the branch as committed, files not committed yet are removed (ignored ones stay). The changes are first kept ([Backups](#backups)). Refused during an unfinished merge (`abort_merge()` first). Agents can't do this with git: `git restore` and `git checkout -- <file>` write the index, which lives under the read-only `.git`.
- **`set_submodule(repo, path, ref, url?)`**: puts a submodule on a commit of its own repo, and adds it first with `url` ([below](#submodules)).
- **`handoff`** never commits: it names a committed branch, and refuses while the agent has uncommitted changes. `commit` is the one way to commit.

Foreman runs one git command at a time per repo, so git's own lock never collides. Its reads (the `status` of every worktree, for the project's [Deployment](../features/project-team.md) section, refreshed on each agent git action) take no optional lock (`GIT_OPTIONAL_LOCKS=0`): they never write the index, so they can't hold `index.lock` while an agent's git needs it. And a git command cancelled midway (a browser request dropped) gets SIGTERM, on which git removes its lock files, and a kill only 5 s later; a kill straight away once left a stale `index.lock` in a lead's worktree, blocking its merges until the CEO deleted it (2026-10-18), and its git runs with the repo's hooks and fsmonitor turned off, so nothing configured in a repo runs a program on the host when Foreman acts. Whether a commit is signed depends on whose it is ([Signing](#signing)). git's housekeeping after a commit (`maintenance`, `gc`) runs inside the command that triggered it, never detached: a detached one would escape the one-command-per-repo rule and could hold the repo's locks while Foreman's next command needs them (found 2026-10-20). The [session prompt](./session-prompt.md) tells agents that git writes go through the tools.

What this buys: no agent can damage refs, or plant a hook or a `.git/config` setting that would run a program on the CEO's machine the next time git runs there; every commit is authored as the agent who made it; and branch rules hold by construction, since Foreman is the only writer. **Trade-off, accepted:** every agent can still read every branch of the repo, its teammates' included.

**Later option, not built:** hide git from agents entirely, mounting only the worktree and no `.git`. Agents would no longer see other branches, at the cost of `diff`, `log` and `blame` inside the container, unless Foreman offered them as tools.

## Submodules

A worktree keeps its submodules' git data under its own git dir (`<repo>/.git/worktrees/<name>/modules/`), read-only in the container like the rest of `.git`, so agents can't fill a submodule or move it. Foreman does, on the host (the CEO, 2026-10-19: Foundry repos keep their dependencies as submodules under `lib/`):

- **In step with the branch.** After it opens a repo, and after `switch`, `merge` and `abort_merge`, Foreman checks each submodule out at the commit the branch pins (`git submodule update --init`), fetching what's missing, and removes the folder of a submodule the branch no longer has, when nothing was changed in it (a plain checkout leaves it behind, and the next `commit` would add it back); its git data stays, so a switch back needs no fetch. Nested submodules only with `recursive_submodules = true` ([Project config](../models/project-config.md)). An agent starts without a submodule that can't be fetched, rather than not at all: the next switch or merge tries again and says so in its result.
- **Relinked when a worktree moved.** Git links a submodule to its git data, and the data back to its folder (`core.worktree`), with relative paths, and `git worktree repair` leaves both alone. So when a worktree moves (moving a project into its workspace put every sandbox one folder deeper), every git command in it fails, `switch` included (found 2026-10-30). At each agent start Foreman rewrites both links for every checked-out submodule, nested ones too, still relative. It runs on the host over a `.gitmodules` the agent can edit, so it only rewrites a submodule's existing `.git` file, inside the worktree, through no symlink, pointing into the worktree's own git dir. Renaming a repo can't move a worktree with submodules at all: `git worktree move` refuses, and the rename says so.
- **Nothing in the CEO's repo config.** Each command gets the URLs of the branch's `.gitmodules` on its command line, and always checks out (a `.gitmodules` can ask for `merge`, `rebase` or `none`): the repo's `.git/config` is never written.
- **`set_submodule(repo, path, ref, url?)`** puts the submodule at `path` on `ref` (a branch, tag or commit of its repo), discarding what was changed in its files, and commits that on the caller's branch, authored as the caller; with `url`, it adds the submodule first (`.gitmodules` and the pin, in one commit). The change reaches the CEO's branches only through the CEO's merge. During a merge it only stages, settling a submodule conflict, and the agent's `commit` concludes the merge.
- **Changes inside a submodule** can't be committed (the repo stores only the commit a submodule is on): `switch`, `merge`, `handoff` and `request_merge` refuse while a submodule has changed files, whatever `.gitmodules` says to ignore, and name them; `set_submodule` discards them.
- **A submodule conflict** has no markers, so `commit` refuses while one is unsettled, rather than let `git add` settle it on whatever the folder is on.
- **A repo inside a worktree that isn't a submodule** (an agent's `git clone` or `git init`) is refused by `commit`: git would commit a pointer to a commit no one else has.
- **Fetches never carry the CEO's credentials**: no global or system git config (credential helpers, a keychain, URL rewrites), no credential helper of the repo, no SSH agent, no prompt, an empty home (no `.netrc`), and **https only**, for nested submodules too. An agent picks these URLs: with the CEO's credentials it could pull any private repo the CEO can reach into its sandbox, and from there out to the network. **The CEO's own checkout comes first**: when `<repo>/.git/modules/<name>` holds the pinned commit, the submodule is copied from it, locally: nothing is downloaded, and it is what the CEO fetched, which agents can already read since the repo's `.git` is mounted in their containers, so no credential is lent, and never from the URL `.gitmodules` gives (the CEO, 2026-10-30; first since 2026-11-04, when a team on 11 repos sat at `starting` while every worktree downloaded every submodule: each worktree keeps its own submodule data). Only when the checkout lacks the commit does it go to the network, and then **shallow**: that commit only (`--depth 1`), not the history (the CEO, 2026-11-04). An `ssh` or scp-style URL is tried as its https counterpart (`git@github.com:org/x.git` → `https://github.com/org/x.git`), so a public dependency comes whatever its URL. Every fetch gives up after 2 minutes and runs in a session of its own (no terminal for ssh to ask anything on), so a remote that never answers can't hold an agent's start. Not in the checkout, and not over the network either: the error says to run `git submodule update --init <path>`, or a fetch, in the CEO's checkout. A URL relative to the repo's remote is refused. Nested submodules never come from the CEO's checkout, and only over https: the copy is one submodule, never recursive, since a nested `.gitmodules` could name any repo on the machine.

## Hand-offs

A hand-off is a message naming a branch: `handoff(mara, "wt/ledger/tove/LED-44", summary)`. Every worktree shares the repo, so the lead can review the branch at once (`git diff` in its own worktree) and merge it with `merge`; nothing is fetched or copied, and agents never push anywhere.

## Branch policy

| Who | May hand off or request a merge of |
|---|---|
| Member | `wt/<project>/<self>/*` only |
| Lead | `lead/<project>/<team>/*` only: the lead works only on its lead branches, never on `wt/` ones; it catches up with the branch its merge request goes into, when that moved, by merging it in (`merge("main")`), never by rewriting the branch |
| Nobody | the CEO's branches (every branch but an agent's, the default branch included): they change only by the CEO's merge or the CEO's own git |

### Where the policy is enforced

By Foreman, never by hooks in the repo: agents can't write `.git` at all, and Foreman is the only one that writes it, through the tools:

- **`open`**, **`switch`**, **`commit`**, **`merge`**, **`abort_merge`**, **`discard`** and **`set_submodule`** act only on the caller's own worktrees and the branches checked out there; **`handoff`** accepts only `wt/<project>/<self>/*`; **`request_merge`** only the caller's own `lead/<project>/<team>/*`, into a branch of the CEO's, never an agent's; **`prune`** deletes only the caller's own branches, and the lead's teammates' merged ones, never one checked out ([Cleaning up branches](#cleaning-up-branches)) ([Protocol → Team tools](./protocol.md#team-tools)).
- **Agents never push, and nothing is pushed on its own.** Only the CEO's **Create PR** on a merge request makes Foreman push the lead branch to the **forge** from the host, with the forge account's token ([Forge adapters](./forge-adapters.md)); agents never receive forge tokens. Calling `request_merge` again on a lead branch whose merge request is still open refreshes it (after merging its target in, or new integrations): Foreman reruns the checks, and pushes again if it has a PR. Lead branches only ever move forward: nothing is rebased.
- **Merge** is Foreman merging the branch into its target on the host, on the CEO's click; with or without a forge ([Pipeline and merges](../features/pipeline-and-merges.md#review-and-merge)). It pushes nothing: "Merge means merge, not push" (the CEO, 2026-11-06).

### Signing

Decided by the CEO (2026-11-06): "if my config says commits should be signed, commits made from my account should be signed; anything agents do should not be signed; anything merged to my branches should be committed by me". So Foreman doesn't override signing on every git command:

- **Commits by the CEO's git identity follow the CEO's git config** (`commit.gpgsign`): the squash commit of Merge (built with `git commit-tree`, which ignores `commit.gpgsign`, so Foreman passes `-S` when it is true; [Pipeline and merges → Merge to a target](../features/pipeline-and-merges.md#merge-to-a-target)), and Foreman's other commits in the CEO's name: wiki edits from the UI, the [global repo](../models/home.md#the-global-repo)'s saves, the project repo's scaffold, a new repo's first commit. If signing fails (no SSH or GPG agent reachable from Foreman's process, a passphrase prompt with no terminal), the commit fails with git's error; a Merge then moves nothing.
- **Agents' commits are never signed**: `commit`, `merge` and `set_submodule`, by the agent's identity, always carry `commit.gpgsign=false`, so nothing an agent does is signed with the CEO's key.
- **Foreman's fallback identity** (when git has no user) never signs, and neither do [backups](#backups) (`refs/foreman/…`, made with `git commit-tree` without `-S`).

## Project knowledge base

The [project repo](../models/project-config.md#the-project-repo) `<workspace>/project/` (`project.toml` and the wiki) is **one live checkout**, mounted into every container of the project: read-write for the **lead** (the lead of each team deployed on the project), read-only for everyone else, enforced by the mount mode. Its `.git` is read-only for every agent, the lead included: the lead edits the files and calls `commit()`, which commits on the project repo's `main` directly: no branches, no merge requests. Everyone else contributes through the [`contribute`](./team-tools.md#tools) team tool: Foreman writes the contribution into `<workspace>/project/wiki/inbox/` and tells the lead, naming that path. There is no writable folder for read-only agents.

**Several leads, one checkout.** Each team deployed on the project has its own lead, and they all share this one checkout. A lead's `commit()` naming `project` takes everything changed in it, so it can sweep another lead's unfinished edit into its own commit: nothing is lost, only the attribution suffers. Accepted for v1; a worktree per lead, with Foreman merging each commit into `main`, is an option for later ([backlog](../../backlog/index.md#not-yet-scheduled)).

**Foreman commits its own writes** to the project repo, one commit per write, like the [global repo](../models/home.md#the-global-repo)'s one commit per save: a `contribute` note authored as the contributing agent, a checkbox tick or card move from the UI authored as the CEO. Each commit holds only the file Foreman wrote, so the lead's uncommitted edits in other files are left alone. When the file itself already has changes nobody committed (the lead mid-edit, or an entry an agent created and hasn't committed yet), Foreman writes it but doesn't commit it: the change goes into the lead's next commit, rather than the lead's edits being committed as the CEO's (the CEO, 2026-10-17).

**Changes to `project.toml` by the Chief of Staff** come later, and how they are approved is decided then ([Project config with the Chief of Staff](../../backlog/cos-project-config.md)). Nothing in the project repo is pushed on its own: the CEO pushes its `main` with **Sync** in Project settings ([Forge adapters → Sync](./forge-adapters.md#sync-the-reserved-repos)) ([Pipeline and merges](../features/pipeline-and-merges.md#review-and-merge)).

## Checks

`checks` from `project.toml` (e.g. `npm test`) run "in a sandbox before handoff and on a merge request". The container image must contain the project's toolchain for this to work ([Agent images](./tech-stack.md#agent-images): the project layer carries the toolchain).

Foreman runs them itself, in a **throwaway container** from the project's image on a clean checkout of the branch: before a handoff is accepted (the member's branch) and on `request_merge` (the lead branch). A clean checkout makes the result reproducible and immune to local state in a worktree. The result is the `checks_status` of the [work item](../models/work-item.md) (handoff) or of the [merge request](../models/merge-request.md) (`request_merge`); when a forge is configured, its CI statuses are shown alongside ([Forge adapters](./forge-adapters.md)).

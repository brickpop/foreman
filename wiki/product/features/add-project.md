# Add a project

A project is a record in Foreman's database plus its [workspace](../models/project-config.md#the-workspace), a folder of the CEO's holding its [project repo](../models/project-config.md#the-project-repo) (`<workspace>/project/`) and its agents' worktrees; its code repos live anywhere in the CEO's home folder ([Project config → The project record](../models/project-config.md#the-project-record)). **Foreman never clones code**: a code repo is one the CEO already has, or a new empty one Foreman creates at a path the CEO picks. Only a project repo can be cloned, with the CEO's own git.

## The dialog

A modal ([App shell](./app-shell.md#overlays)) opened from **`+ New project`** in the sidebar and from the checklist's **A project** row ([First run](./first-run.md#the-checklist)), fresh at each opening. Two steps:

1. **New project**: the **Project name** (any words, made a slug: [Names](#names)), the **Workspace**, then the **Project repo**, a segmented New | Clone:
   - **Workspace**: a path, following the name as `<projects folder>/<name>` (`GET /api/folders/workspace?name=`, from the `projects_folder` [setting](../models/global-settings.md)) until the CEO edits it. "Your folder for this project: its project repo and its agents' worktrees, where you can run their code. Anywhere in your home folder.", plus, when the projects folder doesn't exist yet and the workspace is in it, "<folder> doesn't exist yet: it is created with the project." Picking it in a folder browser comes with [Restructure the New project dialog](../../backlog/new-project-dialog.md).
   - **New**: "Its wiki and project.toml, in a new git repo: the workspace's project/ folder. One left there by a removed project is taken over as it is."
   - **Clone**: a field for a git URL or a local path ("Cloned with your own git: your SSH keys and credential helper. Foreman stores nothing."). The button reads `Cloning…` while it runs.

   **Create project** (Enter too) calls `POST /api/projects`; a refusal shows under the fields, git's own message for a failed clone. On success the project's Wiki opens behind the dialog (no team on it yet), with the toast `<name> created` ("Made its project repo at <path>, with project.toml and a starter wiki.", "Cloned its project repo into <path>.", or, for a [takeover](#effect), "Took over the project repo left at <path>, as it was.").
2. **Repos of `<name>`**: [picking repos](#picking-repos), as many as the CEO likes, each added at once; the line above lists those added; with none yet it reads "Add the code repos agents work on, here or later on its Repos page. With none, they work in its wiki only (research, say)." **Done** closes it, with or without repos ([Team tools → No code repo](../architecture/team-tools.md#no-code-repo)). The project exists from step 1: closing the dialog keeps it, and its repos are added later on its [Repos](./repos.md) page.

## Picking repos

The same form adds a repo from the dialog and from [Repos](./repos.md#the-list) (`AddRepo`), a segmented **Existing repo | New empty repo**:

- **Existing repo**: the folder browser picks a git repo (its **Pick** button), or a pasted path (**Use**). The chosen path shows with **Change**. The **Repo name** follows the folder's name, made to fit the [rules](#names) (`My Repo` → `My-Repo`), until the CEO edits it. A repo without a `main` branch also shows **Default branch**, a select of its branches (the checkout's preselected): "This repo has no branch named main. Pick its default: agents start their branches from it, and merges go to it unless the lead names another target. You can change it later in Repos." ([Project config → The project record](../models/project-config.md#the-project-record)). **Add repo**.
- **New empty repo**: the browser picks the folder it goes in (**Here**, or a pasted path), and the name (required) is its new folder: "Creates <folder>/<name> with a README in a first commit, on main." **Create repo**.

**The folder browser** (`RepoPicker`, from `GET /api/folders?path=`, behind the [access token](../architecture/security.md#access-token) like every request) shows one folder at a time: its path on top, `..` to go up, then its subfolders by name (case-insensitive), hidden ones left out, a git repo's top folder (its own `.git` folder) marked `git`. A click on a folder opens it. It opens at the folder `foreman` was started in (its real path, or `$HOME` when that is outside `$HOME`), a convenience, and goes up to `$HOME`, never above. A folder outside `$HOME`, given by path, is refused (`400 INVALID`); a subfolder whose real path leaves `$HOME` (a symlink out) or is inside Foreman's home isn't listed. A browser can't tell where a dropped folder is on disk, by design: hence the browser and the pasted path.

**`$HOME` bounds every path, never inside Foreman's home** (the CEO, 2026-10-28, replacing the start-folder bound of 2026-10-20): a workspace, and a code repo whichever way it comes (the browser, a pasted path, **Locate**, a new empty repo's folder), by its real path. A path outside is refused with the reason ("… is outside your home folder (…)", "… is inside Foreman's home (…)").

## Names

A **project's name** is a slug (the CEO, 2026-11-02): lowercase letters and digits in words joined by single hyphens (`my-portfolio`), at most 63 characters; it is the project's id and its workspace folder, and the UI shows it readable ("My portfolio", [Project config → The project record](../models/project-config.md#the-project-record)). The dialog takes any words and makes the slug as the CEO types (accents dropped, anything else between words a hyphen: `My Portfolio!` → `my-portfolio`), its hint saying `Its folder and id: <slug>. It shows as <Readable>.`. Projects made before keep their names (`Ledger.v2` still works, shown as it is).

A **repo's name** follows a repo's rules: letters of either case, digits, `.`, `-` and `_`, starting with a letter or digit, at most 63 characters, never hidden. Names of both are unique in any case: a Mac's filesystem takes `Ledger` and `ledger` for one, and elsewhere they would be two names hard to tell apart. A repo is never named `project` (in any case): that is the project repo's place in a sandbox.

## Effect

`POST /api/projects {name, clone?, workspace}` ([API](../architecture/api.md)). Without `clone`, **New**:

1. Refuses a name that breaks the rules (`400 INVALID`), or one taken, in any case, by a project (`409 EXISTS`), and a workspace that breaks [its rules](../models/project-config.md#the-workspace): not absolute, outside `$HOME` or inside Foreman's home, inside a code repo (`400 INVALID`), a file, or overlapping another project's (`409 EXISTS`).
   **A project repo already there** (`<workspace>/project/`, left by a project removed with its project repo kept) is **taken over** as it is, its history and edits included, with no new commit: steps 2 to 4 are skipped and the record is made (the CEO, 2026-10-20; the place redefined 2026-10-28). Only a git repo's own top folder is taken over; otherwise `409 EXISTS` with what to do: Clone asked for ("create the project without Clone to take it over, or move it away"), or not a git repo, a symlink included ("move it away, or pick another workspace"). A failed takeover never deletes that folder. The answer is `201` for a project repo made or cloned, `200` for one taken over, so the dialog can say which.
2. Creates the workspace and its missing parents, then `<workspace>/project/`.
3. Writes `project.toml`, the scaffold's first file (`internal/home/starter/project.toml`), with the defaults ([Project config](../models/project-config.md)): an empty `checks`, the gates as a commented-out starter list (`# always_ask_ceo = ["new dependency", "touches shared staging"]`) so the CEO sees the option, and a `[forge]` table with `kind = "none"`.
4. Creates the **scaffold**: the project repo's files besides `project.toml`, from Foreman's starter, a folder laid out as in the repo and built into the binary (`internal/home/starter/`, `{project}` standing for the project's name). One definition, also used to [fill a project repo that lacks them](./wiki-reader.md#no-wiki-yet). The default is modelled on Foreman's own wiki and workflow (the CEO, 2026-10-17):
   - **`AGENTS.md`**, at the repo's root, outside the wiki bundle: the project's conventions for its agents, in one file. How to operate the wiki with the `wiki` command; the structure below (technical debt kept as one page; decisions written into the spec they change, no folder of their own); specs (`status: planned | partial | built`, open questions in the spec); one task entry per task in `backlog/` (`type: task`, `title`, `status` among `backlog` (unscheduled), `todo` (scheduled), `blocked` (with a `Blocked by` line in the body saying on what), `in-progress` (also while reviewed), `done`, and no other (the CEO, 2026-10-17: five statuses, since a board shows any other as a column of its own), `priority` among `quick`, `high`, `medium`, `low`, `assignee` as an agent id, `epic`, a work-kind tag); epics in `backlog/epics/`; the lifecycle (capture, work, finish, retire); technical debt; the queries. The lead alone writes the wiki and keeps the board true, committing with `commit()`; everyone else uses `contribute()`. Every session prompt points agents at it ([Session prompt](../architecture/session-prompt.md)).
   - **`wiki/wiki.toml`**: `types = ["spec", "task", "epic", "note"]`; `backlog/**` and `inbox/**` kept out of `wiki orphans`; `../AGENTS.md` ignored (outside the bundle); three boards, the two over tasks laned by priority (`lanes = ["quick", "high", "medium", "low"]`; `quick` is work with no uncertainty, doable right now): **Board**, the scheduled tasks (`status!=backlog`) in the columns `todo`, `blocked`, `in-progress`, `done` (the CEO, 2026-10-17: about four columns as a start; `review` went, since reviewed work is still in progress); **Backlog**, the unscheduled tasks and the scheduled ones not started yet in `backlog` and `todo`: its `where` leaves out every status of work started or ended, ours (`blocked`, `in-progress`, `done`) and the usual others an agent might use instead (`doing`, `wip`, `review`, `in-review`, `testing`, `closed`, `cancelled`, `canceled`, `wontfix`, `archived`), so a stray status never lands on it: a card moved to `todo` stays there and shows on Board too (the CEO, 2026-10-17); and **Epics**, the epics by status (the CEO, 2026-10-17: two task boards rather than six columns).
   - **`.gitignore`**, at the repo's root, with defaults that fit any project repo (the CEO, 2026-10-17): the `wiki` command's index (`.wiki/`), secrets (`.env`, `.env.local`), and operating-system and editor clutter (`.DS_Store`, `Thumbs.db`, `desktop.ini`, `*.swp`, `*~`, `.idea/`, `.vscode/`, `.obsidian/`). A project made before it gets the usual notice and `Create it`.
   - **`wiki/index.md`**, titled with the project name, linking product, backlog and technical debt, and saying "Deploy a team from this project's Deployment section."
   - **`wiki/product/index.md`** (the product map), **`wiki/backlog/index.md`** (the current goal and the queries), **`wiki/technical-debt.md`**.
   - Nothing optional: `research/`, `product/glossary.md` or another folder (`discovery/`, `issues/`…) is described in AGENTS.md and created by the lead when there is something to put in it, never as an empty placeholder that invites agents to fill it (the CEO, 2026-10-17).

   The new wiki passes `wiki check`. The wiki can't be read without `wiki.toml` and `index.md`; the rest it reads fine without. The lead creates everything else. Then runs `git init` (on `main`) and commits `project.toml` and the scaffold as the repo's first commit, "Project repo".
5. Creates the project's record: no repos, the default profile.

With `clone` (a git URL or a local path), **Clone**: the same refusals, then `git clone` into `<workspace>/project/` with the CEO's own git on the host (their SSH keys, agent and credential helper; Foreman stores nothing), then the record. A local folder is copied, never moved in. Hardened, since the source is typed in: only the `https`, `http`, `ssh`, `git` and `file` transports (`protocol.allow`), a source starting with `-` refused, `--` before the arguments, and no terminal to prompt on (a session of its own, `GIT_TERMINAL_PROMPT=0`), so a source that wants a password fails with git's message instead of hanging. A failure is `400 INVALID` with git's message. The clone is taken as it is: one without `project.toml` or a wiki shows the usual notices and their `Create it` ([Wiki reader → No wiki yet](./wiki-reader.md#no-wiki-yet)).

Nothing is left behind if a step fails: the folders the call made are removed whole, the workspace's missing parents included (a taken-over one stays). Marking every existing wiki entry as seen is not built yet: it needs the [UI state](../models/ui-state.md) API.

## Code repos

A project starts with none, and deploying refuses until it has one. Each route answers with the project, or a refusal that says why (`400 INVALID`, `409 EXISTS`, `409 DEPLOYED`):

- **Add** an existing repo, `POST /api/projects/{id}/repos {name, path, defaultBranch?}`: an absolute path to a git repo's top folder (its `.git` a folder), with at least one commit, inside `$HOME` and outside Foreman's home ([Picking repos](#picking-repos)), and not already in the project. Its default branch is its `main` branch when it has one; otherwise the request's `defaultBranch` names one of its branches, and a missing or unknown one is refused (`400 INVALID`). `GET /api/folders/branches?path=` lists a folder's branches and its checkout's, for that pick. A repo may be in several projects.
- **New** empty repo, `POST /api/projects/{id}/repos {name, path, new: true}`: a `path` that doesn't exist yet, in a folder that does, inside `$HOME` and outside Foreman's home. Foreman creates it on `main`, its default branch, with a `README.md` in its first commit (so agents' branches have a `main` to start from), and removes it if a later step fails.
- **Default branch** of a repo, `PUT /api/projects/{id}/repos/{repo}/default {branch}`: one of its branches, else `400 INVALID`. Allowed while a team is deployed: worktrees made before stay on their branches; new branches and merges use the new one, which becomes a target if it wasn't one; the old one stays a target, and open merge requests keep theirs.
- **Remove a target** of a repo, `DELETE /api/projects/{id}/repos/{repo}/targets/{target}`: not the default branch (`400 INVALID`), not while a merge request into it is open (`409 IN_USE`). Its branch stays in git.
- **Locate** a moved repo, `PUT /api/projects/{id}/repos/{repo} {path}`: inside `$HOME`, and the folder must hold the repo's root commit. Existing worktrees follow it (`git worktree repair`) on the next start.
- **Rename** a repo, `PUT /api/projects/{id}/repos/{repo}/name {name}`: refused while a team is deployed on the project (`409 DEPLOYED`), and for a repo with a problem (locate it first). The new name follows the [rules](#names) (a change of case only is refused, as a name taken in any case). Each agent's existing worktree moves to the new name (`git worktree move`), so stopped deployments keep their work; if one fails, those moved go back. The project's **open** merge requests on the repo follow the new name, in the same transaction as the record; closed ones keep the old name, their history (the CEO, 2026-10-20).
- **Remove** a repo, `DELETE /api/projects/{id}/repos/{repo}`: refused while a team is deployed on the project (`409 DEPLOYED`). Its folder and branches stay.

## Removing a project

`DELETE /api/projects/{id}` (`?deleteRepo=true`, `?deleteWorktrees=true` for the options), `204` on success, from **Remove this project** in [Project settings](./project-settings.md). Only an [archived](../models/project-config.md#the-project-record) project can be removed (`400 INVALID`, `archive <id> before removing it`; the CEO, 2026-10-23: archiving, which keeps everything, comes first), and never while a team is deployed on it (`409 DEPLOYED`). In order:

1. With the worktrees option (off by default), its agents' sandboxes (`<workspace>/agents/`) go, uncommitted work included, and each code repo prunes its worktrees' records (`git worktree prune`). The repos and their branches stay. Without it, they stay in the workspace, the CEO's files (the CEO, 2026-10-28); their branches can't be deleted while checked out there. [Remove a stopped deployment's worktrees](../../backlog/remove-worktrees.md) is the same action for one deployment.
2. Its session logs (`~/.foreman/logs/*@<id>/`) and its agents' harness folders (`~/.foreman/harness/<id>/`: their conversations) go.
3. Its record and its **history** go, in one transaction: deployments, instances, team messages, actions, work items, merge requests, requests (the CEO, 2026-10-20). Ids are built from the name (`atlas@ledger`), so a redeploy after re-adding the name would otherwise revive the old rows: re-adding it starts clean.
4. With the project repo option (off by default), its project repo folder goes too. Without it, it stays in the workspace, and a new project in the same workspace takes it over ([Effect](#effect)).
5. The workspace itself goes only when nothing is left in it.

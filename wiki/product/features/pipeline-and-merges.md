# Pipeline and merges

How work moves from a member's worktree to a [target](#merge-targets): its repo's default branch (`main`, say) or another. Only the team **lead** asks for changes to reach a target, with a **merge request**; only the **CEO** decides, on the branch's [review](./reviews.md): Merge (Foreman merges locally), Request changes, or Dismiss; Create PR on the forge comes later. Nothing reaches a forge unless the CEO asks. Branch rules: [Sandboxes and git policy](../architecture/sandboxes-and-git.md). Forge calls: [Forge adapters](../architecture/forge-adapters.md).

The pipeline has two kinds of entries, both shown in the [project pipeline](./project-pipeline.md) (In flight and Merged in the project's [Deployment](./project-deployment.md) section). Built so far (2026-10-17): work items ([Work item → Phasing](../models/work-item.md#phasing)) and merge requests ([Merge request → Phasing](../models/merge-request.md#phasing)); since 2026-10-21 decided on their branch's page in [Reviews](./reviews.md).

- **Work items** ([model](../models/work-item.md)): one agent's branch on its way into the lead branch. Informational only: a handoff never creates a request and needs nothing from the CEO.
- **Merge requests** ([model](../models/merge-request.md)): the lead's request to merge a lead branch into a target, carrying every work item integrated since the last one. A merge request is the only pipeline entry that raises a [request](./requests.md): the **review**.

Approvals, questions, findings and blocked requests are independent of the pipeline: agents and Foreman raise them whenever they happen, typically long before any merge request exists ([Requests](./requests.md)).

## Work item stages

| Stage | Label | Entered when |
|---|---|---|
| 0 | in worktree | A member works on `wt/<agent>/<card>`, the branch for one board card |
| 1 | handed to lead | The member calls `handoff(lead, branch, summary)` ([Team tools](../architecture/team-tools.md)) |
| 2 | lead reviewing | The handoff is delivered into the lead's session. Requesting changes (an `ask` to the author) moves nothing; the author's next hand-off of the branch brings it back to stage 1 ([Protocol → Work items and merge requests](../architecture/protocol.md#work-items-and-merge-requests)) |
| 3 | integrated | Merged into one of the lead's `lead/<team>/*` branches in the lead's worktree; checks run |

Each work item carries a short **note**. Deployment → In flight colors it by a **tone** (`ok`, `err`, `ask`, neutral) derived from the work item's state, never stored, e.g. "checks pass" (`ok`) or "2 review comments" (`ask`).

## Review and merge

Only the lead calls `request_merge(branch, entry, into?)`, naming one of its own lead branches (`lead/<own team>/*`; anything else is an error) and a wiki entry, usually the task card, that explains what was done, and where it lands ([Merge targets](#merge-targets)). Foreman runs the project `checks`, creates a **merge request** for each repo in which the branch has new commits, all in the branch's one [review](../models/review.md), and raises the review's **review** request. The merge request carries the work items whose branch head is contained in that lead branch (git ancestry) and that aren't in another merge request yet; they leave "In flight" and are listed under it. **Several merge requests can be open at once**: a lead can have several lead branches, each with at most one open merge request, and other teams' leads on the same project have their own. Calling `request_merge` again on a branch whose merge request is open refreshes it (see *When a target moves*). The CEO reads the change on the review's page in Foreman ([Reviews](./reviews.md)), with git, or on the forge after Create PR. The lead can't pick the repos: a repo where the branch has new commits gets its merge request, and the CEO ticks which ones to merge.

The review request's card shows the entry's title and the repos, and opens the review, where the CEO comments and decides:

| Action | What Foreman does |
|---|---|
| **`Merge to <target>`** (primary), for the repos ticked | Merges the branch into each ticked repo's target on the host, as [below](#merge-to-a-target). Each merged merge request and its work items move to "Merged", the lead is told, the review request resolves once nothing is left open, and merged branches are deleted under the existing rule ([Branches](../architecture/sandboxes-and-git.md#branches)). If the branch doesn't merge cleanly, nothing changes: the merge request is marked "conflicts with `<target>`" and the lead is asked to merge the target in (*When a target moves*) |
| **`Create PR on <forge>`** (only when the repo has a forge) | Pushes the branch and opens a pull request on the forge, recording its URL and number; the request then shows **`Open PR ↗`** instead, and the CEO merges there. Foreman polls the PR ([Forge adapters](../architecture/forge-adapters.md#pr-state)), see below |
| **`Request changes`** | Sends the draft comments (each with its repo, file and line, or general) and an optional note to the lead in one message ([Reviews → What the lead gets](./reviews.md#what-the-lead-gets)). The review waits on the lead; its next `request_merge` on the branch raises the review again, with the new diff |
| **`Dismiss`** | The work isn't wanted. Asks what becomes of its team and branches ([Reviews → A review's page](./reviews.md#a-reviews-page)): the team keeps working, or stops; the branches stay, or are dropped, only with a team stopped or no longer running (its agents work in them). One request: the team stops first, and when it can't, nothing is closed. Then every repo still open closes (and its forge PR, once there are PRs), and a team that keeps working has its lead told to stop work on it ([Reviews → What the lead gets](./reviews.md#what-the-lead-gets)). Its work items stay with the closed merge requests, out of In flight, until a new hand-off of one of their branches frees it. **Dropped branches**: the lead branch and the members' branches its work items carry, in each repo; each head is first kept under `refs/foreman/dismissed/<review>/<branch>`, recoverable by hand. A branch checked out in a worktree can't be deleted, so it moves to its target instead: what that worktree held not committed (a merge not finished included) is kept first under `<backup>@uncommitted`, then the worktree is made clean ([Sandboxes and git policy → Backups](../architecture/sandboxes-and-git.md#backups)). Only a git error keeps a branch, and the close answers which and why |

The lead can take a review back before the CEO decides, and Foreman does when the CEO merges a review that holds all of another open one of the same lead ([Reviews → Withdrawn](./reviews.md#withdrawn)).

After Create PR, the forge is watched:

| On the forge | Foreman |
|---|---|
| Merged | Marks the merge request merged (`merged_at`), resolves the review request, tells the lead. The merge request and its work items move to "Merged". Foreman fetches the new target into the repo, where every worktree sees it |
| Closed without merge | As Dismiss with the team working and the branches kept: marks the merge request rejected, resolves the review request, tells the lead to stop work on it. Not built: [The forge](../../backlog/git-forge.md) |
| Review comments or "changes requested" | Delivers them to the lead (typed into its session when it is idle; [Protocol](../architecture/protocol.md#text-into-a-session-deliveries-and-markers)); the merge request stays open |

**Only the code repos have merge requests.** The [project repo](../models/project-config.md#the-project-repo) gets the lead's `commit()` straight on `main`, and the [global repo](../models/home.md#the-global-repo) gets the UI's saves, the Chief of Staff's confirmed proposals included ([Chief of Staff](./chief-of-staff.md)); both reach their forge only through Sync.

The forge is chosen per project ([Project config](../models/project-config.md)); its token lives in the CEO's [secrets](../models/secrets.md), on this machine. Supported: GitHub, Forgejo, Gitea, `none`. Without a forge, Create PR is not offered.

### Merge targets

Decided by the CEO (2026-11-02; [Merge targets](../../backlog/archive/merge-targets.md)). Work can land on several branches of a code repo, say `release/2.0` while other work lands on `main`.

- **A target** is a branch of one code repo that only the CEO's merges write. Each repo has **one list of targets**, one of them flagged its **default branch** ([Project config → The project record](../models/project-config.md#the-project-record)): where work starts and merges go unless the lead names another. No agent commits to a target, and **anything merging into a target is approved by the CEO only**, on its review.
- **The lead creates targets**: `create_target(repo, name, from)` makes a new branch `name` in one code repo at `from`, and records who made it, at which commit and when. `from` is one of the repo's targets (`main`) or a commit one holds (a hash of an older `main`): **a target starts only from work the CEO already merged** (the CEO, 2026-11-02, after review). So it is a target at once: it changes no code and holds nothing unreviewed, so it needs no approval. A target spanning repos is one call per repo, each from its own commit. Refused: a name the repo has as a branch (whoever made it) or as a target, its default included; one that isn't a valid branch name, or is in an agents' namespace (`wt/*`, `lead/*`); a `from` the repo doesn't have, or that no target holds (a lead branch's unmerged work, say); a repo that isn't one of the project's code repos; any caller but the lead.
- **Work starts from its target**: `switch(branch, from?)` makes a new branch from `from`, a target, in every repo that has it (from the default branch where it doesn't); without it, from the default branch. A `from` no repo has as a target is refused; on a branch that exists already it changes nothing, and the answer says so. A target is where the work has to *start*, not only where it lands: a branch made from `main` and merged into `release/2.0` would carry `main`'s newer commits into the release.
- **The lead names where it lands**: `request_merge(branch, entry, into?)`. Without `into`, a new merge request goes to its repo's default branch, and a refreshed one keeps the target it has (the CEO may have changed it); with it, into `into`. A review spans every repo where the branch has new commits, so `into` must be a target of each of them, and of every repo the review already has open (they move with it: a review never splits between targets unasked): if any lacks it, the request is refused, naming those repos (the lead creates it there first, or splits the work), and nothing is made or moved; it never falls back to another branch. A target whose branch is gone from git is refused too. The review shows each repo's (`api → release/2.0`) and its button reads `Merge to release/2.0` when all ticked repos go to one; its diff, conflicts and "what counts as merged" are reckoned against that target, and a forge PR's base will be it. A branch started from another target isn't refused: the commits it would bring along show in the diff, for the CEO to see.
- **The CEO can change it** on the review, before deciding, repo by repo, to another of that repo's targets: the diff is then against it, a conflict found before is forgotten (the next merge tells), comments on its removed lines are outdated (they were the old target's lines, as on a forge when a PR's base changes), and the lead is told.
- **Between targets** (a release fix back into `main`): an ordinary merge request. The lead makes a branch from the destination, merges the source target in with `merge(<target>)`, and requests the merge into the destination; the CEO approves it like any other.
- **When a target moves**, the notice of [When a target moves](#when-a-target-moves) goes to the leads of the open merge requests into that same target of that repo. **Idle desks follow the default branch only**: an agent's home branch tracks its repo's default; work for another target lives on topic branches started from it, never on an idle desk.
- **The CEO sees and removes them** in [Repos](./repos.md): each repo's targets after its default, each with who made it, from which commit and when. Removing one stops it being a target (the branch stays in git), refused while a merge request into it is open; the default branch can't be removed, only changed. **Git says whether a target exists**: one whose branch was deleted outside Foreman is forgotten within 30 s, unless a merge request goes into it; that review then says the target is gone, shows no diff and can't merge that repo until the CEO picks another target. A missing default branch is flagged on its card, and agents can't start.
- **Changing a repo's default branch** moves the flag: the branch picked becomes a target if it wasn't one, and the old default stays a target. Merge requests keep the target they have.
- **Agents ask for the targets** with `targets()`, every agent ([Protocol → `targets`](../architecture/protocol.md#targets)): each repo's, the default first, the others with who made them and at which commit. They are never in the [session prompt](../architecture/session-prompt.md) (the CEO, 2026-11-02), so making or removing one leaves every prompt as it was.

### When a target moves

Open merge requests into the same target race each other: when one is merged, the others may now be behind the target, or conflict with it. **Nothing is ever rebased: the lead catches up by merging the target in**, and Foreman never resolves conflicts itself; it tells the lead who has to:

- When a merge request is merged (by Merge, or seen on the forge), Foreman delivers a notice (typed into the session when it is idle) to the lead of **every other open merge request into the same target of the same repo**: `From Foreman: main moved in api (lead/atlas/integration was merged). Merge it into lead/atlas/settlement-v2 with merge("main"), resolve any conflicts and commit(), then call request_merge again.`
- If the forge reports an open PR as conflicting with its target, or Merge finds a conflict, the repo shows **conflicts with `<target>`** (`--err`) on its review and the lead gets the same line.
- The lead calls `merge("<target>")`: Foreman merges the target into the lead branch in the lead's worktree ([Agents and git](../architecture/sandboxes-and-git.md#agents-and-git)). Conflicts go back to the lead, who resolves the markers and calls `commit`. Then it calls `request_merge` again on the same branch. Foreman reruns the checks, pushes the branch to its PR when there is one (a plain fast-forward: the branch history is never rewritten) and refreshes the request. The merge request and its review request stay the same.

### Merge to a target

Decided by the CEO (2026-10-17; a squash since 2026-10-21, replacing a merge commit; into any target since 2026-11-02). The CEO's own checkout of the repo (`<project>/<repo>/`) is never left out of step with the target:

- **Only the commit the CEO read**: the merge names the branch's head as the review page showed it, and a branch that moved since isn't merged ([Reviews](./reviews.md)).
- **Always a squash**: one new commit on the target with what the branch changes, by the CEO's git identity (Foreman's when git has none), its message the title of the merge request's wiki entry and nothing else: no `Co-Authored-By` trailers (the CEO, 2026-10-29; the merge request and the branch's history say who wrote it). The agents' work-in-progress commits never reach a target; each accepted piece of work is one commit there, revertable as one. When the target has all of it already, nothing is committed.
- Foreman builds that commit without a working tree (`git merge-tree --write-tree`, `git commit-tree` with the target as its one parent). **When the CEO's checkout has the target checked out**, the target then fast-forwards there to it, so its files move with it; if the CEO has uncommitted changes it would overwrite, git refuses and nothing changes: the review request says to commit or stash, then merge again. **Otherwise** (another branch, or detached), the target is moved, and only if it is still where it was read; the CEO's files are not touched.
- Either way, a conflict changes nothing: the merge request is marked "conflicts with `<target>`" and the lead is asked to merge the target in.
- **The merged branch then moves to the target as it is now**, however it was merged (here, on the forge, by hand): its commits are not in the target, so a next review of it would show them again. It moves only while it is still at the commit that was merged; where it is checked out (the lead's worktree), its files follow and the lead's uncommitted changes are kept (`git reset --keep`). When it can't (the lead committed since, or an uncommitted change is in the way), it stays, and the lead is told to merge the target into it first ([Protocol → Deliveries Foreman originates](../architecture/protocol.md#deliveries-foreman-originates)).
- **Idle desks follow the new default branch**, after a merge into it only: every agent's home branch in that repo (`wt/<agent>/main`, `lead/<team>/integration`) holding nothing the default lacks, with nothing uncommitted where it is checked out, moves to it ([Sandboxes and git policy → Branches](../architecture/sandboxes-and-git.md#branches)). A desk with work stays as it is.
- **What counts as merged** (here, and for a merge seen outside Foreman): merging the branch into its target would change nothing (`git merge-tree` gives the target's own tree). A squash, a rebase or a merge commit on the forge all pass; a branch whose commits are in the target is only a special case.
